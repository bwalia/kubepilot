The 2am problem

Every Kubernetes incident starts the same way. Something pages you, maybe a Slack alert or a customer, and you open a terminal and start typing: kubectl get pods -A, describe, logs --previous, get events --sort-by. Ten tabs later you're still trying to connect a CrashLoopBackOff to the ConfigMap someone changed an hour ago, while node memory pressure quietly evicts the neighbours.

Most of an incident is spent working out what is actually wrong, not fixing it. KubePilot targets that gap. It's an open-source troubleshooting cockpit that correlates events, pods, nodes and logs, explains the failure in plain English, and can safely apply the fix.

Three modes, one incident loop

KubePilot is built around three modes that match how SREs actually work an incident: ask, verify, act.

🧠 CoPilot: diagnose

AI-assisted troubleshooting. Ask what's broken in plain English, or hit AI Analyze on a failing pod.

  • Automated RCA with evidence chains, a confidence score, risk, commands and YAML fixes
  • Anomaly detection for CrashLoop, OOMKilled, ImagePull and node pressure
  • Runs on Ollama and local models, so your cluster data stays yours
  • Copy Prompt to reuse a diagnosis with any LLM you like

🔎 Pilot: verify

A Lens/Rancher-style, read-only SRE browser for checking what the AI told you.

  • Deployments, StatefulSets, DaemonSets, Jobs, Services, Ingresses, ConfigMaps, Secrets and PVCs
  • Pod workbench: containers, events, live logs and sanitized YAML
  • Topology canvas: Ingress → Service → Workload → Pod
  • Multi-cluster kubeconfig switching with no restart

🛠️ AutoPilot: remediate

Closed-loop self-healing with real safety rails, so you can trust automation after hours.

  • Three modes: off, dry-run (preview only) and active
  • Policy gates: namespace blocklists, action allow-lists and confidence floors
  • Cooldowns and hourly caps to prevent remediation storms, plus a one-click pause kill switch
  • A decision ledger of every executed, skipped, escalated and failed action
🔁

The loop: CoPilot explains, Pilot verifies, AutoPilot remediates. Each mode feeds the next, so there's no copy-pasting pod names between a chatbot, a terminal and a runbook wiki.

What's new in KubePilot

Recent releases focused on making the incident loop faster, more trustworthy and easier to reach:

Durable RCA history

An optional embedded SQLite store keeps RCA reports and anomalies across restarts, with configurable retention and WAL journaling. It needs no CGO and still ships as a single binary. When the same pod crash-loops again next week, the previous root cause is already there.

Pre-built and custom runbooks

Seven opinionated diagnostic workflows ship out of the box. Drop your own YAML runbooks into a directory and they hot-reload via fsnotify. A user runbook overrides a built-in one with the same ID, so your team's tribal knowledge becomes executable.

Cluster resource gauges and real node IPs

Live CPU, memory and storage gauges with a per-StorageClass breakdown. They're Longhorn-aware, so you see physical disk usage, not just bound PVC totals. Node views now classify LAN, WAN and WireGuard/flannel tunnel addresses instead of showing only the k3s overlay IP, which matters when the incident is a networking one.

Port-forwarding from the UI

Open a tunnel to a pod or service directly from the dashboard and reach it through the built-in reverse proxy. Sessions are listed, cancellable and auditable, with no stray kubectl port-forward left running in a forgotten terminal.

Accurate health numbers everywhere

Pod counts and health classification now match exactly between the web dashboard, the iOS app and the cluster itself. Completed Jobs count as completed, not failing, so the "failing" number you act on during an incident is the real one.

Slack incident cards

Built in and off by default. Set a webhook and a minimum severity, and KubePilot posts anomaly detected and RCA finalized cards with summary, confidence and a deep link back to the dashboard. 

KUBEPILOT_SLACK_WEBHOOK_URL=https://hooks.slack.com/services/XXX/YYY/ZZZ
KUBEPILOT_SLACK_MIN_SEVERITY=high
KUBEPILOT_NOTIFIER_DASHBOARD_URL=http://your-host:8383

Native iOS companion

A SwiftUI app talks to the same KubePilot APIs: health cards, pod search, live logs, events and RCA reports, plus Face ID, home-screen widgets and Siri/App Intents. You can triage from your phone before you reach a laptop.

MCP for agents

A built-in MCP server exposes KubePilot to AI agents for multi-cluster orchestration and programmatic access, so your own agents get the same diagnostics the dashboard uses.

How it resolves incidents faster: a worked example

1

Signal

The anomaly detector flags payments-api crash-looping in prod. A Slack card arrives with severity HIGH and a dashboard link. You open it on your phone.

2

Diagnose (CoPilot)

CoPilot has already run RCA: the container exits non-zero on startup because a required env var from a recently edited ConfigMap is missing. The report shows the evidence chain (events → logs → config diff) and a confidence of 95%.

3

Verify (Pilot)

In Pilot you open the pod workbench, check the previous container logs and the ConfigMap YAML, and use the topology view to confirm the blast radius: one Service, two Ingress routes.

4

Fix (AutoPilot)

AutoPilot in dry-run previews the remediation. Once you're happy, switch to active or apply the suggested YAML fix. Risky actions need CR-code approval. Every decision lands in the ledger for the post-incident review.

5

Remember

The RCA is stored in SQLite. Next time the pattern shows up, the history is one click away, and your custom runbook can encode the fix.

⏱️

The result: you don't start triage by gathering context. KubePilot correlates events, node pressure and pod failures for you, and the AI summary gives the next engineer the full picture without a long handoff.

Safe by default

  • Optional dashboard auth (basic or bearer token) and strict CORS origins
  • Read-only Pilot browsing; kubeconfig and action mutations are gated behind explicit flags
  • AutoPilot defaults to off or dry-run, with confidence floors and a kill switch
  • Local LLMs via Ollama, so cluster logs don't have to leave your network
KUBEPILOT_DASHBOARD_AUTH_ENABLED=true \
KUBEPILOT_ENABLE_KUBECONFIG_MUTATIONS=false \
KUBEPILOT_ENABLE_ACTION_MUTATIONS=false \
./dist/kubepilot serve --dashboard-port=8383

Get started in minutes

Install with Helm, Docker, plain manifests or systemd. The Helm route:

helm repo add kubepilot https://bwalia.github.io/kubepilot
helm repo update
helm upgrade --install kubepilot kubepilot/kubepilot -n kubepilot --create-namespace
kubectl port-forward svc/kubepilot -n kubepilot 8080:8080
# open http://localhost:8080

Full options are in the README. For a deeper look at the three modes, see the KubePilot home page.
